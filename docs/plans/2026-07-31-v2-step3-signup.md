# 배포 3 — 가입 대상 3분류 계획 **r3** (2026-07-31)

r1 = NO-GO(치명 3·중대 8), r2 = REVISE(새 치명 1·중대 6).
두 차례 시니어 검토 지적을 전부 반영한 실행판. 이전 판의 오류는 §12에 남긴다.

## 0. 사용자 확정 사항

| 항목 | 결정 |

## 2. 시트 — 열을 **끝에 추가**

```
MEMBERS_학생   : email, 이름, 학년반, active, 가입시각, 가입경로, [학교]   ← G열 추가
MEMBERS_학부모 : email, 이름, 자녀이름, active, 가입시각, 가입경로        ← 변경 없음
MEMBERS_성도   : email, 이름, 소속전도회, active, 가입시각, 가입경로      ← 신규
MEMBERS_교사   : 변경 없음 (교사 시트 관련 코드는 손대지 않는다)
```

**중간에 끼우면 안 되는 이유 (r2의 메커니즘 설명 정정)**
`ensureTab_`은 1행 **라벨만** 덮어쓰고 데이터는 옮기지 않는다. 중간 삽입 시
`active` 라벨 아래에는 빈 칸이 아니라 **옛 `가입시각` 값**(예 `2026-01-15`)이 온다.
`isActive_`는 이 값도 `true`로 본다 → **탈퇴 계정 부활**, 그리고
`active`·`가입시각`·`가입경로` **3열이 함께 어긋난다.**
끝에 붙이면 기존 열이 움직이지 않는다. 다만 **G열이 이미 쓰이고 있으면 같은 사고**가
나므로 배포 절차에서 선점검한다(§10-2).

| 15 | `scripts/gas-harness.mjs` | 스키마 사본(29~42행) **+ `makeSheet` 시드 배선(223~226행)** | 테스트가 실제와 다른 스키마로 통과 |

### ★ #10이 왜 치명적인가
`load.js`는 **모든 사용자에 대해 무조건** `getMyPrayers`를 부르고, 실패하면
`{ok:false, code}`를 돌려준다. 성도의 기도 액션을 `forbidden`으로 막으면 이 경로가
그대로 걸려 → `failToLogin('forbidden')` → **「기록을 불러오지 못했습니다」 + 로그인 화면**.
성도는 날주도 자료도 볼 수 없다.
게다가 「실패를 빈 데이터로 갈음하지 않는다」는 규칙은 `check-web`과 `test-web-views`가
**일부러 강제하는 불변식**이라 우회할 수 없다. **#7(서버 차단)보다 #10을 먼저 고친다.**

## 6. 개인정보

1. **만 14세 미만** — 담임교사가 **우리반 학부모에게** 오프라인 동의를 이미 받았다.
   앱에 고지·동의 UI를 두지 않는다.
   - ★ 그런데 이 동의는 **성도 분류에는 미치지 않는다.** 가입코드 1개를 3분류가 공유하므로
     만 14세 미만이 「성도」로 자가등록하는 경로가 열려 있다.
     → **완화**: 성도 선택지에 «성인만» 안내 1줄(§5). 이는 동의 요청이 아니라 **대상 안내**라
     §0의 «동의 UI를 두지 않는다»와 충돌하지 않는다.
     `docs/ops/06-operations.md`에 교사의 성도 명부 사후 점검 절차를 넣는다.
   - `[추정 — 1차 조문 미대조]` 개인정보 보호법 제22조의2는 만 14세 미만 아동의 개인정보
     «처리» 자체에 법정대리인 동의를 요구한다. 수집 항목이 적다고 면제되지 않는다.
     실제 근거는 **오프라인 동의를 받았다는 사실**이며 그 경위는 앱 밖에 있다.
2. 전화번호를 뺐지만 **학교가 새로 들어온다.** 「이름+학교+학년」의 식별력이 제거분을 일부
   상쇄하므로, 학교를 **앱 응답에서 제외**하는 §0 결정이 중요하다.
3. **가입코드 교체 절차**를 `docs/ops/06-operations.md`에 추가.
4. 기존 가입자 소급 없음. 학교는 빈 값. 응답·화면에 안 나가므로 표시 규칙 불필요.
5. **분류 이동**(성도→학생 등)은 교사가 시트에서 행을 옮긴다 → `06`에 절차 추가.

## 7. 회귀 검사

### GAS 하네스 (실행 검증 — mutation 필수)
1. 성도 토큰 → `getMembers`/`getAllRecords`/`getAllPrayers` 전부 `forbidden`
2. 성도 토큰 → `addPrayer`/`getMyPrayers`/`setPrayerAnswered`/`deletePrayer` 전부 `forbidden`
3. 성도 토큰 → `getMyRecords`/`setRecord`는 **정상 동작**
4. 성도의 `setRecord` → `RECORDS.구분`이 `'성도'`
5. 미지 kind로 `kindLabel_` → 오류
6. 성도 email의 학생 재가입 → `already_registered`
7. `register(kind:'teacher')` → `bad_request` + 교사 행 수 불변 *(기존 유지)*
8. 학교가 **올바른 열**에 저장됨 — `h.sheet(...).data[0]`을 직접 변형해 열 순서를 바꾼 뒤 확인
   (현 하네스에 헤더 오버라이드 시드가 없다. 기존 관행을 따른다)
9. 구 헤더(학교 없음) 시트에 학생 register → **`server_misconfig`**
10. 학교·소속전도회에 `=SUM(A1)` → `'` 접두 저장
11. 우선순위 **전수**: 성도+교사 / 학부모+성도 / 학생+성도 → 각각 상위 채택
12. `parent`·`member`가 `school`을 보내도 **어디에도 저장되지 않음**
13. `getAllRecords` 응답에 `구분='성도'` 행이 없음
14. harness `HEADERS`/`SHEET_NAMES` ↔ `Sheet.gs` **양방향 키 집합 비교**
    (값만 비교하면 새 키 누락을 못 잡는다)
15. 셀 수 상한 테스트를 **현행 100명 시드 유지** — 성도가 우리반에서 빠져 전제가 그대로다

### 프론트 (test-web-views — 실행 검증)
16. ★ `kind='member'` 세션에서 `loadMyData`가 **`getMyPrayers`를 호출하지 않고** `{ok:true}` 반환
    (fetch 스텁으로 호출된 action 목록을 모아 단언)

### 정적 (check-web) — *존재 확인일 뿐이라고 정직하게 표기*
17. 가입 화면에 분류 3개와 분류별 입력란이 **존재**
18. 홈 카드 `tab:` 리터럴이 **정확히 4개** 유지 *(기존 검사 — 필터 방식이라 깨지지 않음)*

## 10. 배포 절차 — **서버(GAS) 먼저, 웹 나중**

> 순서를 바꾸면 사용자가 「혜림교회 성도」를 골랐을 때 서버가 모르는 값이라 원인 불명 오류가 난다.
> 이 순서가 안전한 이유: **배포된 버전은 고정되어 있어 편집기에 붙여넣은 코드가
> 라이브에 즉시 반영되지 않는다** `[추정 — GAS 버전 배포 동작]`. 그래서 3~5를 먼저 해도 안전하다.

1. 스프레드시트 → **파일 → 사본 만들기**
2. **`MEMBERS_학생`의 G열이 비어 있는지 눈으로 확인.** 비어 있지 않으면 그 내용을 옮긴 뒤 진행
3. Apps Script에 `Sheet.gs`·`Auth.gs`·`Actions.gs`·`Setup.gs`·`Code.gs` 붙여넣기
4. ★ **`Setup.gs`의 `SETUP_SHEET_ID` «하나만» 채운다.**
   나머지(`SETUP_OAUTH_CLIENT_ID`·`SETUP_ADMIN_EMAIL`·`SETUP_REGISTER_CODE`)는
   `PASTE_...` **그대로 둔다** — 그러면 기존 스크립트 속성이 보존된다.
   (r2는 «3개 다 채우라»고 했는데, 구글 로그인 키를 한 글자라도 틀리면
    **전 사용자가 로그인 불가**가 된다. 채울 필요가 없다.)
5. `setupAll` 실행 → 로그에 **`SETUP COMPLETE`** 확인
6. 시트에서 눈으로 확인: `MEMBERS_성도` 생성, `MEMBERS_학생` **G1이 정확히 «학교»**
   (손으로 타이핑하지 말 것 — `setupAll`이 써 준다. 앞뒤 공백이 있으면 `server_misconfig`)
7. **배포 관리 → 수정 → 새 버전** (주소 유지)
8. 웹앱 주소를 브라우저로 열어 **`build` 값이 올라갔는지 확인**
9. **그 다음에** `git push`
10. `docs/ops/05-test-checklist.md` 재실행 (성도 계정으로 탭 3개인지 포함)
