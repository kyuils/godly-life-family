## D. B1 「로그인이 안 된다」 — 진단 3문항 (다른 작업보다 먼저)

**가설 순위** (검토 지적 반영):
1. **B1 = D1** — 카카오톡 인앱 웹뷰에서 구글 로그인은 `disallowed_useragent`로 **차단된다.** 증상이 정확히 "로그인이 안 된다"다. 두 신고가 같은 결함일 수 있다.
2. **가입 흐름** — 현재 명부에 교사 1명뿐이라 다른 사람은 전원 `unauthorized` → 가입 화면. `REGISTER_CODE` 미전달이면 `bad_code`, 폐쇄면 `registration_closed`. 셋 다 "로그인이 안 된다"로 보인다.
3. 직전에 고친 화면 전환 결함의 잔재(서비스워커 캐시).

**질의 3문항** — 코드 수정 전에 반드시 답을 받는다:
1. 어느 앱에서 열었나 (카카오톡 / 크롬 / 삼성인터넷 / 사파리)
2. 화면 아래에 뜬 `[코드]` 문구 원문 (또는 스크린샷)
3. 가입코드(`youth2026`)를 입력하는 화면까지 갔나

**진단 없이 인증 코드를 고치지 않는다** (보안 불변식 1 보호).

### ■ 배포 2 — 서버 무변경. `web/sw.js`의 `BUILD_TAG` 상향 **필수**

**E-A1/A2/A5 자료 개편**

*데이터 — ★ additive. `paras`를 지우지 않는다*
- `sections[].items[{no, paras, refs}]`를 **추가**하고 기존 `paras`는 **그대로 둔다.**
  이유: `web/data/*`는 cache-first라 구 JSON + 신 JS 조합이 발생한다. additive면 그 조합에서도 화면이 죽지 않고, 롤백이 파일 하나 되돌리기로 끝난다.
- **항 분리 규칙 (검토 지적으로 교체)** — 초판의 `(N)` 규칙은 1장에서 확정적으로 실패한다:
  ```
  각주 문단 = /^\(\d+\)/ 로 시작  OR  (직전 문단이 각주이고 '(' 로 시작)
  항 = [연속된 본문 문단들] + [뒤따르는 연속된 각주 문단들]
  ```
  → 각주 연속행 `(눅 16:29, …)`은 앞 각주에 흡수되고, 성경 66권 목록 24문단은 다음 각주까지 한 항의 본문으로 묶인다.
- **검증 (개수 검사만으로는 부족)**
  1. 33개 장의 항 수가 표준과 일치 — 표준 항 수의 출처를 테스트 주석에 `[확정]`으로 명기. 못 대면 `[추정]` 표기
  2. 모든 항의 본문이 비어 있지 않음
  3. 항 번호가 1..N 연속
  4. **골든 픽스처 3개** — 1장 1항 첫 30자 / 1장 10항 / 33장 마지막 항 끝 30자 문자열 일치
  → **하나라도 실패하면 중단하고 보고.** 데이터를 억지로 맞추지 않는다.
- `index.json`에 `group` 필드 추가

*화면 — 2단 → **1단**으로 축소 (과설계 지적)*
- 목록: 분류 그룹 제목 + 카드
- 본문 상단 **☰** → 시트 **1단**: 위 = 문서 목록, 아래 = 목차 → 자료 간 즉시 이동 (A1 해결)

**B2 홈 화면** — ★ **탭으로 추가하지 않는다** (탭 6개 = 직전에 고친 결함의 재발)
- 로그인 후 첫 화면 = 홈. 큰 아이콘 4개: 날주 체크 / 날주 진행 / 기도 요청 / 신앙 자료

### ■ 배포 3 — 가입 3분류. **별도 계획서 + 별도 시니어 검토 후 착수**

여기만 GAS 재배포와 시트 변경이 걸린다. 이번 계획서에서는 **설계 방향만 확정**하고 실행하지 않는다.

*시트 — ★ 열을 중간에 끼우지 말고 **끝에 추가***
```
MEMBERS_학생   : email, 이름, 학년반, active, 가입시각, 가입경로, 전화번호, 학교
MEMBERS_학부모 : email, 이름, 자녀이름, active, 가입시각, 가입경로, 전화번호
MEMBERS_성도   : email, 이름, 소속전도회, active, 가입시각, 가입경로, 전화번호   (신규)
MEMBERS_교사   : 변경 없음
```
- 모든 I/O가 헤더 **이름 기반**이라 순서에 의미가 없다. 끝에 붙이면 기존 열이 한 칸도 안 움직여 **마이그레이션이 불필요**해진다.
- `학년반`을 `학년`+`학교`로 **분해하지 않는다**(`Auth.gs`·`Actions.gs`가 `학년반`을 하드코딩, 기존 시드도 전부 `학년반`).
- **초판의 오류**: "`ensureTab_`이 헤더를 덮어써 열이 밀린다"고 썼으나, `register` 경로가 쓰는 것은 `Sheet.gs`의 `ensureSheet_`이고 이것은 기존 헤더를 고치지 않는다. 진짜 위험은 **소유자가 `setupAll`을 재실행할 때 `active` 열이 빈 칸으로 밀려 비활성 계정이 부활**하는 것이다(빈 값 = active).

*서버 — 수정 대상 함수 (초판에 하나도 없었음)*
| 함수 | 왜 |
|---|---|
| `Actions.gs findAnyMemberRow_` | 3시트만 스캔 → 성도가 학생으로 **재가입 가능**(중복 가입 차단 우회) |
| `Auth.gs lookupMember` | 3시트만 판정 → **가입은 되는데 로그인이 안 됨** |
| `Auth.gs kindLabel_` | 미지 kind를 `'학생'`으로 폴백 → 성도 기록이 **'학생'으로 위조** |
| `Auth.gs isTeacher_`/우선순위 | 우선순위를 `교사 › 학부모 › 학생 › 성도`로 계약에 확정 |
| `web/js/view-class.js`, `app.js` 배지 | 교사 화면에 성도가 안 보이거나 학생으로 섞임 |

- `kindLabel_`은 미지 kind에 **폴백하지 말고 오류**로 처리한다(조용한 오분류 금지).
- **`getMembers` 응답에 전화번호를 넣지 않는다.** 근거: 교사 토큰 하나가 뚫리면 전 명부 전화번호가 한 번에 새어 나간다. 시트에만 두면 유출 표면이 구글 계정 1개로 줄고(요구사항 8의 설계 의도), 교사는 시트에서 언제든 본다. → 회귀 검사로 고정.
- **헤더 누락 방어**: 대상 시트에 신규 필수 열이 없으면 `register`가 `server_misconfig`를 반환한다. 없으면 전화번호가 **조용히 버려지고** 가입은 성공한다.
- **전화번호 저장**: `010-1234-5678` 형식으로 정규화(앞자리 0 소실 방지). `sanitizeCell_`은 신규 필드에도 적용.

`§0.1`(kind는 student|parent만) · `§2.1~2.4` · `§4 액션표` · `§4.2 register` · `§7 화면` · `§9 범위밖` — 전부 충돌한다. 코드보다 계약을 먼저 고친다.

## H. 초판(r1)의 오류 기록

1. `ensureTab_`/`ensureSheet_`를 혼동. 열 밀림 위험을 잘못된 메커니즘으로 서술했고 실제 위험(**비활성 계정 부활**)을 놓쳤다.
2. 3분류 확대에 필요한 서버 함수 4곳을 하나도 적지 않았다.
3. WCF `(N)` 휴리스틱이 1장에서 실패하는 것을 확인하지 않고 계획에 넣었다.
