## 2. 요청 2 — 앱으로 설치 안내

### 2.1 무엇을 만드나 (★ r2에서 위치가 바뀜)

**로그인·가입 화면**에 설치 안내를 둔다. 홈이 아니다.

r1은 «로그인 후 홈 위쪽»이라고 했는데 셋 다 잘못이었다:
- 사용자 원문은 「**가입고 로그인시**」다 — 그 화면이 맞다.
- 홈에 띠를 얹으면 요청 3이 되찾은 56px을 **그 자리에서 도로 까먹는다.**
- 로그인하면 사라지는 화면이라 «닫으면 다시 안 뜨게» 상태가 **필요 없다**
  → `localStorage`가 불필요해지고, 아래 2.3의 위반이 통째로 사라진다.

로그인 화면에는 이미 `#inapp-banner`가 같은 자리를 쓰는 검증된 패턴이 있다.

### 2.2 기기별로 갈린다 (이게 핵심)

| 환경 | 방법 | 화면 |
|---|---|---|
| 안드로이드 크롬·삼성인터넷 | `beforeinstallprompt` 이벤트를 잡아 뒀다가 `prompt()` | 「홈 화면에 추가」 버튼 |
| iOS 사파리 | 이벤트가 **없다**. 자동 설치 불가 | 「공유 → 홈 화면에 추가」 그림 안내 |
| 카카오톡 등 인앱 | 설치 불가 | **안 띄운다** (이미 «브라우저로 열기» 안내가 있다) |
| 이미 설치됨 | — | **안 띄운다** |

### 2.3 판정 규칙

- 이미 설치: `matchMedia('(display-mode: standalone)').matches` 또는
  `navigator.standalone === true`(iOS)
- 인앱: 기존 `detectInApp(navigator.userAgent)` 재사용
- ~~닫으면 다시 안 뜬다: `localStorage`에 «닫음» 표시~~ → **★ r2에서 폐기**
  - `check-web.mjs:120`은 `web/js/*.js` **전 파일**에서 `localStorage|sessionStorage|
    document.cookie`를 금지한다(예외는 `mccheyne-plan.js` 하나). 보안 불변식 7의
    **유일한 자동 가드**다. 쓰려면 그 가드에 구멍을 뚫어야 하고, 그 구멍은
    앞으로 추가되는 모든 파일에 열린 채로 남는다.
  - 위치를 로그인 화면으로 옮기면 이 상태 자체가 필요 없다(§2.1).

### 2.3b ★ r2 — 반드시 챙길 배관 3가지

1. **`beforeinstallprompt`를 모듈보다 먼저 잡는다.** `index.html`의 `<script type="module">`은
   암묵적 defer라, 캐시된 재방문에서는 이벤트가 모듈 평가 **전에** 발화해 안내가
   «떴다 안 떴다» 한다. `<head>`에 인라인으로 스태시한다:
   `addEventListener('beforeinstallprompt', e => { e.preventDefault(); window.__bip = e; })`
   `prompt()`는 사용자 제스처 안에서 **1회만** 유효하다.
2. **`window.matchMedia(...)`로 점을 붙여 쓴다.** `check-web.mjs:514`의 «정의되지 않은
   함수 호출» 검사는 점 없는 `matchMedia(`를 미정의 호출로 잡는다.
3. **`package.json:8`의 test 체인에 `test-install.mjs`를 넣는다.** 명시적 체인이라
   빠뜨리면 테스트를 쓰고도 한 번도 실행되지 않은 채 통과 선언을 하게 된다.

### 2.3c 기기 분기 (★ r2에서 `manual` 추가)

| 환경 | 모드 |
|---|---|
| 안드로이드 크롬·삼성인터넷·데스크톱 크롬 | `prompt` — 버튼 |
| iOS 전 브라우저(전부 WebKit) | `ios` — 「공유 → 홈 화면에 추가」 안내 |
| Firefox Android·구형 브라우저 | **`manual`** — 「브라우저 메뉴 → 앱 설치」 (r1은 이 칸이 비어 아무것도 안 떴다) |
| 카카오톡 등 인앱 | `none` |
| 이미 설치됨 | `none` |

설치 판정은 `standalone` 외에 `minimal-ui`·`fullscreen`도 함께 본다.

### 2.3d ★ 배포 게이트 — 설치한 상태에서 로그인이 되는지

이 앱의 세션은 **메모리 전용**이다(불변식 7). 카톡 인앱에서 페이지가 다시 읽히자
로그인이 풀린 것이 바로 그 성질 때문이었다. 설치된 iOS PWA는 백그라운드에서
종료되기 쉽고 GIS 팝업도 제약을 받는다.

**안내를 내보내기 전에 실기기에서 «설치 → 아이콘으로 기동 → 로그인 성공»을 확인한다.**
안 되면 iOS 안내는 보류하고 안드로이드만 먼저 낸다. 이것은 자동 테스트로 대신할 수 없다
(로컬에서는 서비스워커를 등록하지 않으므로 `beforeinstallprompt`가 **아예 뜨지 않는다**).

### 2.4 새 파일 `web/js/install.js` (DOM 없이 테스트 가능하게)

```
export function installMode(ua, opts)  // 'prompt' | 'ios' | 'none'
```
- `opts = { standalone, hasPrompt }`
- 순수 함수로 두어 `scripts/test-install.mjs`에서 Node로 검증한다
  (`inapp.js`와 같은 방식 — 이미 그렇게 해서 회귀 9건을 잡고 있다)

## 3. 요청 3 — 탭을 제목줄 안으로

### 3.1 사용자가 원하는 것

`[이름·배지] [탭들] [로그아웃]` 한 줄. 세로 약 60px를 되찾는다.

### 3.2 ★ 정면으로 부딪히는 이전 결정

2026-07-30에 사용자가 **«메뉴가 너무 작아 안 보인다»** 고 신고해서 탭을 키웠다
(아이콘 위·글자 아래, 높이 65px). 한 줄에 밀어 넣으면 그 문제가 되살아날 수 있다.

교사 화면 기준 계산(폭 390px):

```
390 - 좌우 여백 24 - 이름 76 - 로그아웃 62 - 간격 12 = 216px
216 ÷ 5탭 = 탭 하나 43px
```

43px는 손가락 터치 권장치(44px)에 **못 미친다.** 그래서 그대로는 안 된다.

### 3.2b ★ r2 — 요청대로 하면 안 된다는 결론

실제 CSS 값으로 다시 계산했다.

```
고정비 = 좌우 패딩 32 + 갭 16 + 로그아웃 78 = 126px
390px 기기 · 이름 84px → (390-126-84)/5 = 36px
360px 기기 · 이름 84px → 30px
```

탭 안쪽 여백(좌우 8px)을 빼면 **글자가 쓸 수 있는 폭이 22~28px**이다.
「우리반」 세 글자가 10px 폰트로도 안 들어가 「우리…」가 된다.
2026-07-30에 사용자가 신고한 **«메뉴가 작아 안 보인다»가 더 심해진다.**

계약 §7.1과 `check-web.mjs:368`은 «6탭이 되면 작아진다»를 근거로 홈을 탭에서
제외해 뒀는데, 이 변경은 5탭을 그보다 나쁘게 만든다 — 근거가 무너진다.

### 3.3 ★ r2 — 대신 이렇게 한다 (A안: 제목줄이 스크롤로 접힌다)

CSS 두 줄이다.

| 대상 | 지금 | 바꾼 뒤 |
|---|---|---|
| `.appbar` | `position:sticky` | `position:static` |
| `.topnav` | `top:calc(safe-area + var(--appbar-h))` | `top:env(safe-area-inset-top)` |

- 화면을 내리면 이름·로그아웃 줄(56px)이 위로 빠지고 **메뉴만 남는다.**
  상시 점유가 120px → 64px. **56px 회복** — 요청이 노린 것과 같은 크기다.
- **탭 크기는 하나도 안 줄어든다.** 7/30 신고가 재발하지 않는다.
- 앱바 배경(코랄)과 탭 배경(흰색)이 섞이는 문제도 발생하지 않는다.
- 되돌리기: CSS 두 줄.
- `top`은 `env(safe-area-inset-top)`으로 둔다 — 설치 후 standalone에서 노치 아래 붙는다.

**사용자에게 알린다**: 수단이 바뀌었고 목표(아래 내용을 더 보이게)는 그대로 달성된다는 것,
원하시면 요청대로 한 줄에 넣을 수 있으나 탭이 30~36px이 된다는 것.

### 3.3-old (r1, 폐기)

1. **로그아웃을 아이콘으로 바꾸지 않는다.** 비개발자·학생이 쓰는 앱에서 글자
   「로그아웃」은 남긴다. 대신 `sm` 크기로 줄인다.
2. **이름 칸을 줄인다.** 이름만 한 줄로 두고 배지(학생/성도)는 이름 옆 작은 칩으로.
   `max-width: 84px` + 말줄임.
3. **탭은 아이콘 + 글자를 가로로** 두지 않고 **세로 유지**하되 크기를 줄인다
   (아이콘 18px, 글자 10px). 높이 52px.
4. **탭 줄은 가로 스크롤을 유지**한다(`.topnav`가 이미 `overflow-x:auto`).
   폭이 모자라면 잘리지 않고 밀린다.
5. 교사(5탭)는 여전히 빡빡하다 → **교사만 예외로 두 줄**로 두는 것은 하지 않는다.
   대신 교사 화면에서만 이름 칸을 더 줄인다.

> **남는 위험**: 그래도 교사 5탭은 한 탭 43~46px이다. 실기기에서 누르기 어렵다는
> 신고가 다시 오면 «교사만 두 줄»로 되돌린다. 이 사실을 사용자에게 미리 말한다.

### 3.4 검사

`check-web.mjs`의 기존 «메뉴 위치» 검사(`#nav`가 `#view`보다 앞)는 그대로 두고,
`#nav`가 `.appbar-inner` **안**에 있는지로 바꾼다. 안 그러면 예전처럼 화면 맨
아래로 가라앉는 사고가 다시 가능해진다.

## 4. 요청 4 — 자료 화면 머리줄과 2단 목록

### 4.1 머리줄

`.section-head`에 `display:flex; align-items:center; gap`을 준다.
`‹`(왼쪽) — 제목(가운데, `flex:1`, 가운데 정렬) — `☰`(**오른쪽 끝**).

- 지금 `.section-head`는 자료 화면 말고 **다른 화면에서도 쓰는지** 먼저 확인하고,
  쓰고 있다면 `.lib-head` 전용 class를 새로 만든다(다른 화면을 깨뜨리지 않기 위해).

### 4.2 ☰ 시트를 2단으로

첨부 5번 사진처럼 **왼쪽 = 신조와 고백(문서 목록), 오른쪽 = 목차**.

```
.nav-sheet{display:grid;grid-template-columns:minmax(96px,38%) 1fr;gap:…}
```
- 각 단은 **따로 스크롤**한다(`overflow-y:auto`). 목차가 196문답(대요리문답)이면
  한 단만 길어지는데, 같이 스크롤하면 문서 목록이 화면 밖으로 나간다.
- 단 제목(「신조와 고백」/「목차」)은 각 단 위에 고정(`position:sticky`).
- **2단이 좁아지는 문제**(원래 1단으로 둔 이유)는 문서 이름을 2줄까지 허용하고
  (`word-break:keep-all`) 폰트를 줄여 해결한다. 첨부 사진이 실제 휴대폰이므로
  2단이 성립한다는 증거가 있다.

### 4.3 ★ r2 — 「배치만 바꾼다」는 틀렸다

`.nav-sheet`의 **직계 자식**은 지금 평면이다:
`.nav-sec-title` → `.sheet-group`·`.nav-doc` 여러 개 → `.nav-sec-title` → `.nav-toc-list`.
여기에 `grid-template-columns`를 주면 **이 전부가 좌·우로 번갈아 꽂힌다.**
`view-library.js:176-180`을 **두 개의 래퍼 `<div>`로 재구조화해야 한다.**

또 각 단의 독립 스크롤은 `overflow-y:auto`만으로 동작하지 않는다:
- `.sheet-body`의 높이는 flex로 제한될 뿐 **definite height가 아니다** → 자식이 내용만큼
  늘어나 결국 시트 전체가 스크롤된다(= 하려던 것의 반대).
- 그래서 `.nav-sheet{max-height:70dvh}`로 **상한을 명시**하고, 각 단에
  `min-height:0; overflow-y:auto`를 준다. `min-height:0`이 빠지면 grid 자식의 기본
  `min-height:auto` 때문에 또 안 된다.
- sticky 단 제목에는 **배경색을 반드시 준다** — 없으면 내용이 제목 뒤로 비쳐 지나간다.

### 4.4 ★ r2 — 2단의 진짜 비용은 목차 쪽이다

r1은 왼쪽(문서 이름)만 걱정했는데, 실제로 좁아져서 무용해지는 것은 **오른쪽 목차**다.

| | sub가 쓰는 폭(390px) | 보이는 글자 |
|---|---|---|
| 지금 1단 | ≈272px | ≈22자 |
| 2단(38%) | ≈127px | **≈10자** |

대요리문답은 「1문」「2문」 숫자만으로는 정보가 없어 sub가 목차의 실질이다.
→ 2단일 때 `.nav-toc-no{min-width:34px}` + sub를 `white-space:normal`로 **2줄 허용**.

「첨부 사진이 실제 휴대폰이므로 2단이 성립한다」는 r1의 문장은 `[제한적]`이다 —
다른 앱의 콘텐츠가 들어간다는 증거일 뿐이다. 사용자가 원하는 **형태**가 2단임은
확정이고, 성립 여부는 위 수치로 판단한다.
