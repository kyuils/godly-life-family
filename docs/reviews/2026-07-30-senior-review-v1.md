## 정정 — 검토자의 사실 오인 1건

**#16(c)**: 검토자는 "`limit`은 250이 상한이라는 주장을 확인하지 못했다"고 기록했으나,
이는 **계약 작성 전에 직접 호출로 확인한 사실**이다.

```
GET .../eMARKDOWN_USER_LIST?...&limit=300
→ 400  PARAM_ERROR : paramInt(limit) > max value : 250
```

계약 §5.2에 `[확정 — 2026-07-30 직접 호출]`로 근거를 명기했다.
다만 검토자의 부수 권고("`count` 필드로 총량을 확인하고 `skip`으로 전량 수집하여 `limit` 상한에 의존하지 말 것")는
타당하므로 그대로 반영했다.

## 핵심 아키텍처 변경 — 연도별 → 월별 시트 분할

검토자가 "되돌리기 가장 어려운 결정이니 한 번 더 판단하라"고 지정한 항목. 재계산 결과:

| 축 | 연도별 `RECORDS_2026` | 월별 `RECORDS_2026-07` |
|---|---|---|
| 최악 행 수 (100명) | 36,500행 (12월) | **3,100행 (상한 고정)** |
| 달력 탭 접근 단위 | 불일치 (전체 스캔) | **정확히 일치** |
| `setRecord` 락 보유 | 김 (연 전체 스캔) | **짧음** |
| 200일 연속 계산 | 1회 읽기 (36,500행) | 7회 읽기 (누적 21,700행), 공백 시 조기 중단 |
| 시트 탭 수 | 연 1개 | 연 12개 |

연속기록 계산만 월별이 불리해 보이나, 누적 읽기량도 오히려 적고 대부분의 사용자는 1~2개 시트에서 끝난다.
탭 수 증가는 운영 문서로 흡수 가능하고, 시트 생성은 전부 자동이므로 사람이 할 일은 없다.
→ **월별 채택.**
